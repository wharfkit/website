# Wharf 4.0.0

You install `@wharfkit` packages at one version number in 4.0.0, and every package you add resolves the rest of the release with it. The release also carries the API changes developed as `@wharfkit/antelope` 2.0, session keys in `@wharfkit/session`, and a signing reliability fix in `@wharfkit/wallet-plugin-anchor`.

The [upgrade guide](/docs/releases/upgrading-to-4-0-0) covers the procedure, the version each package comes from, and a checklist. This page covers what is in the release.

## Across every package

Every package in the release is version `4.0.0`, whatever version it was on before, and depends on the others by exact version rather than by a range. Installing one brings the matching versions of the rest.

No `@wharfkit` package declares another `@wharfkit` package as a peer dependency. Plugins that declared `@wharfkit/session` as a peer, and `@wharfkit/wallet-plugin-cloudwallet`, which also declared `@wharfkit/antelope`, take both as normal dependencies.

Every package declares `engines: {"node": ">=20.19.0"}`, and both its CommonJS and ES module bundles are compiled to ES2020. In the 1.x and 3.x line the CommonJS bundle was compiled to ES2015, so a toolchain that could only parse the older level still loaded it. The guide lists [which toolchains and browsers this reaches](/docs/releases/upgrading-to-4-0-0#javascript-language-level).

`@wharfkit/cli`, `@wharfkit/protocol-esr` and `@wharfkit/session` re-export a namespace they import from a CommonJS dependency, such as the `zlib` option `session` hands to a signing request. In the 3.x line the CommonJS bundles built that namespace with a `null` prototype and froze it, so `namespace instanceof Object` was `false` and the object rejected writes. It inherits the dependency's own prototype and is not frozen in 4.0.0, which matches the TypeScript sources and the ES module bundles. Reading properties and calling methods behaves the same either way; code that tests one of these namespaces with `instanceof`, `Object.getPrototypeOf` or `Object.isFrozen` sees a different answer, and code that assigns onto one succeeds where it threw in strict mode before.

Every package is licensed under plain `BSD-3-Clause`, with one license text across the repository. Most packages previously carried a no-military-use clause in their license text, some manifests declared it as `BSD-3-Clause-No-Military-License`, and `@wharfkit/signing-request` was MIT.

All development happens in [github.com/wharfkit/js](https://github.com/wharfkit/js), one package per directory under `packages/`. Package names on npm are unchanged. Release candidates publish under the `next` dist-tag and stable releases under `latest`, with npm provenance attached to every tarball.

## @wharfkit/antelope

The changes developed as antelope 2.0, from version 1.2.0.

### Cryptography

`@noble/curves` and `@noble/hashes` replace `elliptic`, `brorand` and `hash.js`.

K1 signatures produced for the same key and message differ from the ones 1.x produced, because the search for a canonical signature feeds its attempt counter through RFC 6979 extra entropy rather than through the old library's personalization string. Every signature the new code produces is valid and canonical, and verification of older signatures is unaffected. A test that asserts a literal signature string needs re-recording.

`PrivateKey.sharedSecret()` returns the full fixed-width 32 bytes of the shared x-coordinate, which is what the specification calls for. The old derivation stripped leading zero bytes, so the two values agree unless the x-coordinate starts with a zero byte, which happens for roughly one key pair in 256. Data encrypted with the old derivation decrypts with the `legacy` option:

```ts
const secret = privateKey.sharedSecret(publicKey, { legacy: true })
```

### Float rendering and parsing

`Float32.toString()` returns the shortest string that round-trips to the same value, so `1.5` renders as `"1.5"` rather than `"1.5000000"`. Infinity and NaN render as the spellings nodeos emits, `inf`, `-inf`, `nan` and `-nan`, and negative zero renders as `-0`. Any snapshot, fixture, or user-facing string built from a `Float32` changes with it.

`Float32.from()` and `Float64.from()` read those spellings back, including `infinity` and a sign. A NaN decoded from the wire keeps its original bytes, so its sign survives re-encoding.

### Authority sorting

`Authority.sort()` compares keys by the ordering nodeos enforces, permission levels by actor and then permission, and waits numerically, where it previously compared the rendered strings. Call it before including an authority in an `updateauth` action, as before. The chain sometimes rejected authorities in the old ordering.

`Name`, `PermissionLevel` and `PublicKey` gained a public `compare()` method as part of this. `PublicKey.compare()` follows the chain's ordering for WebAuthn keys, comparing the key, user presence and rpid as a tuple.

### Table queries on float indexes

`get_table_rows` accepts `Float128` bounds and infers `key_type` for `float64` and `float128` indexes. A `Float128` bound sets `encode_type: 'hex'` and byte-reverses the bound, which is the spelling nodeos reads. `GetTableRowsParams` gained an `encode_type` field, and `Float128` gained `fromDouble()`, `fromDecimal()` and `toBoundHex()`. Existing table queries are unaffected.

### Default fetch implementation

`FetchProvider` looks for `globalThis.fetch` first, then `window.fetch`. Node.js 18 and later ship a built-in `fetch`, so no implementation needs to be passed on any supported Node.js version:

```ts
// before
import fetch from "node-fetch"
const provider = new FetchProvider(url, { fetch })

// after
const provider = new FetchProvider(url)
```

The `fetch` option stays supported for custom implementations and for instrumenting requests.

### Dependencies

`pako` moved from 2.x to 3.x and `bn.js` from 4.x to 5.x. Both are internal to antelope. A project that imports `pako` directly should note that 3.x is ESM and has no default export.

## @wharfkit/session

From version 1.7.0.

### Session keys

An application can hold a key that signs a named set of actions on its own, and hand everything else to the user's wallet. Pass a `sessionKey` configuration to the `SessionKit`:

```ts
const sessionKit = new SessionKit(args, {
  ui,
  sessionKey: {
    whitelist: [{ contract: "eosio.token", actions: ["transfer"] }],
  },
})

const result = await session.setupSessionKey()
```

`setupSessionKey()` generates a K1 key, proposes an `updateauth` that adds it under a permission named after the application, and links the whitelisted actions to that permission. The session then signs a whitelisted action with the stored key and rewrites its authorization to the session key permission; anything outside the whitelist goes to the wallet the user logged in with. A whitelist entry with no `actions` covers every action on that contract.

`Session` also carries `getSessionKeyStatus()`, `validateSessionKeyWhitelist()`, `updateSessionKeyLinks()` and `removeSessionKey()`, which proposes the `unlinkauth` and `deleteauth` that undo the setup.

Session keys need a `UserInterface` implementing `onSessionKeyConsent`, `onSessionKeyConflict`, `onSessionKeyMismatch` and `onSessionKeyRemove`. The `SessionKit` constructor throws naming the missing hooks. `@wharfkit/web-renderer` implements all four.

### Session handoff through a URL

`Session.encode()` returns a session as a `SerializedSession`, a JSON string, a `URLEncodedSession` struct, or an Antelope-encoded hex string, so one application can hand a session to another through a link:

```ts
const payload = session.encode("url")
window.location.href = `https://example.com/?incomingWharfSession=${payload}`
```

The receiving application opts in, and `restore()` then reads the parameter, strips it from the URL so a reload cannot replay it, and falls back to storage when no session arrives:

```ts
const sessionKit = new SessionKit(args, { acceptUrlSession: true })
const session = await sessionKit.restore()
```

`acceptUrlSessionParam` renames the parameter, which defaults to `incomingWharfSession`. Reading the URL requires a browser; under Node.js `restore()` goes straight to storage. A session sent this way carries the wallet data needed to sign, so send it only to an origin you control.

### Choosing when two sessions are the same

`SessionKit` treats two sessions as the same when their chain, actor and permission match, which decides whether persisting a session replaces a stored one and which session a logout removes. `equalityFn` replaces that rule:

```ts
const sessionKit = new SessionKit(args, {
  equalityFn: (a, b) => {
    const first = a instanceof Session ? a.serialize() : a
    const second = b instanceof Session ? b.serialize() : b
    return (
      Session.matches(first, second) &&
      first.data?.appId === second.data?.appId
    )
  },
})
```

An application holding several sessions for one account, separated by something it stores in `session.data`, needs this to keep them apart. `login()`, `logout()` and `persistSession()` each accept an `equalityFn` of their own for a single call. The default is exported as `serializedSessionEquals`.

### Method signatures

`SessionKit.restore()` describes its argument with `PartialSerializedSession`, and the `RestoreArgs` type is removed. The shape is unchanged apart from `walletPlugin`, which is typed as `SerializedWalletPlugin` rather than `Record<string, any>`, so only an explicit `import type {RestoreArgs}` needs editing.

`SessionKit.persistSession()` takes `PersistOptions` in place of a boolean second argument, carrying the same flag and the equality function:

```ts
await sessionKit.persistSession(session, { setAsDefault: false })
```

`URLEncodedSession` exposes the session it carries as `serialized`, replacing `args`.

### Logging out one session

`logout(session)` clears the stored default only when the default held the session being logged out, compared with the same equality function that filters the stored list. Other sessions keep their `default` flag. Before 4.0.0 any logout removed the default for every chain. Nothing is promoted in place of a default that is logged out: the chain has no default until the application chooses one through `restore()` with an actor and permission, or through `persistSession()`. `logout()` with no argument still clears everything.

### Storage writes complete before the promise settles

`login()`, `restore()` and `persistSession()` resolve after the session is in storage, both the default `session` key and the `sessions` list. Two logins in a row on one chain keep both sessions, where the second previously read the list before the first write landed. This matters to any `SessionStorage` whose writes take time to complete, which the interface has always allowed.

`restoreAll()` builds a live session for every stored session with a registered wallet plugin and writes nothing, so stored order and default flags survive the call. It previously looped over `restore()`, which persists, and could rewrite which session a chain treated as its default.

### Wallet plugin instances

`WalletPlugin` gained an optional `clone()`, implemented on `AbstractWalletPlugin`, which returns a copy carrying its own session data. `SessionKit` clones the registered plugin for each session it restores, so several sessions sharing a wallet plugin no longer share one instance's data. `SessionKit.getWalletPlugin(id)` returns a registered plugin by its id.

### Waiting for irreversibility

`transact()` accepts `awaitIrreversible`, which sends through `send_transaction2` with retries enabled and no block limit, and `broadcastOptions` for the underlying `returnFailureTrace`, `retryTrx` and `retryTrxNumBlocks`. Both can be set once on the `SessionKit` or per call.

### Login hooks

`LoginContext` carries the `session` that login produced, readable from an `afterLogin` hook.

## @wharfkit/web-renderer

The renderer draws the four session key flows: the consent prompt listing the contracts and actions the key will cover, the conflict prompt when the permission already holds keys, the whitelist mismatch prompt, and the removal prompt.

`WebRenderer` accepts `colorMode`, which is `'light'` or `'dark'` and sets the theme for both the renderer and the host page:

```ts
const ui = new WebRenderer({ colorMode: "dark" })
```

## @wharfkit/wallet-plugin-anchor

Same-device signing on iOS completes when Safari opens the return path in a fresh tab. The plugin records the pending request before it hands off to Anchor, and connects to the callback channel after the page comes back, rather than holding a WebSocket open across a suspension that could swallow the signature.

The plugin accepts a `transport` option carrying `send`, `waitForCallback` and `generateReturnUrl`, which both transports use. An application can route the buoy traffic through its own implementation or instrument it.

## @wharfkit/protocol-esr

The package exports the helpers behind the Anchor handoff: `storeTransactionHandoff()`, `findReturnedTransactionHandoff()`, `clearTransactionHandoff()`, `receiveReturnedTransaction()`, `isSamePageReturn()` and `waitForPageReturn()`, with the `TransactionHandoff` type they read and write.

## @wharfkit/protocol-scatter

Importing the package succeeds in any environment. `getScatter()` checks for a browser and throws `The Scatter protocol requires a browser environment and cannot be used in Node.js.`, and `scatter-ts` and `eosjs` load only after that check passes, so neither enters a consumer's graph until a browser session starts.

`@wharfkit/wallet-plugin-scatter`, `@wharfkit/wallet-plugin-tokenpocket`, `@wharfkit/wallet-plugin-imtoken` and `@wharfkit/wallet-plugin-gatewallet` import the protocol directly and import cleanly under Node.js.

## @wharfkit/roborovski

`activity()` queries an account's history through the service's v2 route and returns an `ActivityCursor` with `next()` and `prev()`, filters for contract, action and date range, and a page size. `transaction()` reads a transaction by id through the same route. `get_actions()` and `get_transaction()` stay as they were.

## @wharfkit/account-creation-plugin-metamask

The plugin carries its own account creation client instead of depending on `@greymass/create-account`, which pinned its own copies of `@wharfkit/antelope` and `@wharfkit/signing-request`. The published package declares `@metamask/providers` and `@wharfkit/session`, so a project installing it resolves one copy of each Wharf package.

## @wharfkit/account-creation-plugin-anchor

The plugin compares the creation service message against the service's origin rather than against the whole service URL, so a `serviceUrl` with a path works. A `serviceUrl` passed in configuration reaches the account creator, where it was accepted and dropped before.

## @wharfkit/transact-plugin-explorerlink

The plugin builds the explorer link through `ExplorerDefinition.from()`, so a chain whose `explorer` is a plain object gets a link rather than an error.

## @wharfkit/cli

`wharf` uses the built-in `fetch` rather than `node-fetch`. The command surface is `keys`, `account` and `generate`, unchanged from 2.11.0.

## @wharfkit/bundle

The bundle packages the Session, Contract and Account Kits, `@wharfkit/antelope`, `@wharfkit/web-ui`, five wallet plugins, two transact plugins, and the history and token libraries into one file for pages built without a bundler. It re-exports `@wharfkit/web-ui` in place of `@wharfkit/web-renderer`, and adds `@wharfkit/token` and `@wharfkit/roborovski`, whose exports are namespaced alongside `AtomicAssets` and `Hyperion`.

The ES module build is one file, where a dynamic import previously left the published package unimportable. Source maps ship with the tarball. Load it from a CDN by the exact version and full file path, which is the only form that serves the bytes npm published:

```html
<script src="https://cdn.jsdelivr.net/npm/@wharfkit/bundle@4.0.0/dist/wharf.bundle.js"></script>
```

## @wharfkit/light-api

A client for the [Light API](https://github.com/cc32d9/eosio_light_api) service, contributed by [includenull](https://github.com/includenull) and covering all sixteen of its HTTP routes: account details and permissions, token balances, REX balances, top holders and holder counts, key and code hash lookups, the network list and the indexer's sync state. It wraps an `APIClient` you pass in, the same shape as `@wharfkit/hyperion`:

```ts
import { APIClient, FetchProvider } from "@wharfkit/antelope"
import { LightAPIClient } from "@wharfkit/light-api"

const client = new APIClient({
  provider: new FetchProvider("https://eos.light-api.net"),
})
const lightapi = new LightAPIClient(client)

const balances = await lightapi.get_balances("eos", "teamgreymass")
```

This is its first release under the `@wharfkit` name.

## @wharfkit/wallet-plugin-tacklebox

A wallet plugin for [TackleBox](https://github.com/doyen-games/tacklebox), a native wallet and block explorer for Antelope blockchains, contributed by [on-a-t-break](https://github.com/on-a-t-break). TackleBox speaks the anchor-link protocol, so logging in sends an ESR identity request over a buoy callback and opens a sealed push channel that later transactions travel through:

```ts
import { WalletPluginTackleBox } from "@wharfkit/wallet-plugin-tacklebox"

const kit = new SessionKit({
  // ... your other options
  walletPlugins: [new WalletPluginTackleBox()],
})
```

The prompt carries a launch link on the wallet's own `tacklebox:` scheme, a QR code, and a copy fallback, so it works whether or not the wallet is on the same device. This is its first release under the `@wharfkit` name.
